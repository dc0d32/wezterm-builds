dc0d32/wezterm-builds — public, Windows-only build service
=========================================================

This directory is a complete dual-architecture Windows repository payload, not
an activated deployment.
The empty public dc0d32/wezterm-builds repository has been created with owner
approval. No commit, push or release has been published.

Owner bootstrap (manual; not performed by the agent)
----------------------------------------------------
1. Use the existing empty PUBLIC dc0d32/wezterm-builds repository on GitHub.
   Use main as its default branch. Copy this directory's contents into its
   working tree, including .github/, .gitattributes and .gitignore.
   Do not copy any surrounding nixos repository files.
2. Review and commit the payload, then push main. No PAT, app, deploy key,
   repository secret, upstream credential or repository-dispatch token is
   required. Use GitHub-hosted runners, not self-hosted runners.
3. Settings > Actions > General: enable Actions and allow the SHA-pinned
   actions/checkout, actions/upload-artifact, actions/download-artifact and
   actions/cache/save ONLY.
   Restore uses a dependency-free local node20 action from the trusted control
   checkout, not actions/cache/restore or the combined actions/cache action.
   The default workflow token
   may remain read-only: only publish requests contents: write and actions:
   read. No PR creation permission is required or used here.
4. Settings > General > Releases: enable "Release immutability".
   This is REQUIRED for successful publication. GitHub's REST "immutable"
   field is response-only, not a documented create/update input.
   We create a draft, attach verified assets, then publish it, and require
   immutable=true in the returned release. Never send a fictitious flag.
   If the feature is unavailable, this pipeline fails verification; it does
   not claim an editable release is immutable. The documented GET
   /repos/{owner}/{repo}/immutable-releases requires admin read access, which
   GITHUB_TOKEN's contents: write does not provide. Do not broaden the token
   or add a PAT to preflight this setting. The owner must enable it first.
   A setup mistake is detected after the draft-to-public transition: that
   normal but editable release leaves a FAILED run, cannot be deduped/adopted,
   and is never overwritten by this service. This is a platform limitation,
   not a claim of an atomic immutability-setting check.
5. Protect main (restrict writes and require review of workflows/scripts).
   This service intentionally has no pull_request/push/workflow_run triggers.
   Only default-branch schedule and workflow_dispatch runs are accepted.
6. Keep the coordinator's PR OPEN while building. It must be a same-repository
   dc0d32/nixos PR from automation/update-flake-lock against nixos's current
   default branch, carrying the request at .github/wezterm-request.json.
7. Run the "Windows build" workflow manually on main, or wait for the hourly
   :23 poll. GitHub schedules are best-effort and may be delayed/dropped;
   inactivity can disable schedules on public repositories after 60 days.
   Re-enable if needed. API rate limits produce a failed, closed poll; no
   authentication fallback to nixos/wezterm is permitted.

Local verification (Python >= 3.9; stdlib only)
-----------------------------------------------
    python3 -B -m unittest discover -s tests -v
No fixture uses tempfile, mktemp or /tmp. Fixtures are UUID directories under
tests/.test-work and cleaned after each test. On Windows Python is supplied by windows-2025 and windows-11-arm. Builds use
PowerShell 7, stable Rust/MSVC and hosted image tools. The x64 build alone also
uses Git bash, Strawberry Perl, 7-Zip and Inno Setup 6 for upstream packaging.
The Windows builds and native ARM64 validation must be verified with a real

Windows build caches (build job only)
-------------------------------------
Prepare runs BEFORE any cache restore: anonymous exact public source/submodule
checkout, .tag from the source date, stable Rust resolution, and explicit
x64-host/x64-target or x64-host/ARM64-target MSVC/SDK environment resolution.
It hashes the actual candidate Cargo.lock, full upstream source SHA,
rustc/cargo -vV (including host), Windows OS/runner-arch/compile-target,
hosted ImageOS/ImageVersion, cl/link binary hashes, compiler/Cargo environment,
and trusted build/restore/helper/local-action/workflow bytes. Compile recomputes that identity
after restore and fails if it changed. Default-branch and schedule/manual gates
are explicit in the build job, both script phases and every cache-save step.
RUSTUP_TOOLCHAIN=stable explicitly keeps candidate toolchain files from silently
selecting a different compiler than the rustc/cargo identity prepared for caches.

The x64 job caches exactly three paths; ARM64 caches only the first two:
  .cargo-build/registry/cache  crates.io .crate downloads only; environment-scoped
                              fallback permits reuse across source/lock changes
  candidate/target            release AND debug dependencies; fallback retains
                              full environment scope AND exact Cargo.lock hash
  .nextest/bin                x64 ONLY cargo-nextest.exe; exact
                              environment/toolchain and pinned 0.9.114 key
The target triple and compiler environment are part of every cache scope, and
the visible key family is Windows-X64 or Windows-ARM64. Therefore no primary or
fallback key can cross architectures. Registry/target exact keys additionally
include the full 40-character upstream
source SHA and Cargo.lock hash. No OS-only, Rust-only or branch-only fallback.
Changing the build scripts/workflow bumps every environment scope. New image,
native compiler, Rust/Cargo, flags or SDK identities intentionally cause misses.

Only SAVE uses actions/cache/save@0057852bfaa89a56745cba8c7296529d2fc39830
(v4.3.0). Restore uses a dependency-free local node20 action which launches
python -B control/scripts/cache_restore.py. Runtime cache credentials are passed
only to that child process: never to logs, action outputs, GITHUB_ENV, or compile.
The helper requires ACTIONS_CACHE_SERVICE_V2=true and implements the internal
v2 API contract compatible with @actions/cache 4.1.0; this is not a public,
stable API guarantee. GetCacheEntryDownloadURL uses POST to the fixed runtime
cache service origin and fixed
/twirp/github.actions.results.api.v1.CacheService/GetCacheEntryDownloadURL path,
with Bearer runtime-token authentication. Its cache version
hash uses the literal cache path, zstd-without-long, windows-only, and 1.0,
matching the pinned save implementation with cross-OS archives disabled.
Hosted zstd must be present and functional; there is no alternate decompressor
or silent cold-build fallback for a broken decoder. The signed blob download
sends no runtime/API credentials and follows no redirects.
Runtime origins are restricted to results-receiver.actions.githubusercontent.com
or pipeline.actions.githubusercontent.com (including subdomains); downloads to
blob.core.windows.net backends only. These restrictions target GitHub.com hosted
Windows x64 runners, not GHES, custom cache backends or cross-OS archives.

Restore bounds compressed downloads to 10 GiB, expanded archives to 30 GiB,
and tar member count to 300,000. Streaming download/decompression has timeouts,
and zstd's decoder window is capped at 128 MiB. The ENTIRE tar is validated
before materializing members in a private stage inside the workspace. Paths,
entry types, collisions and link targets are checked before manual file copies;
only safe in-root hardlinks are supported, never unrestricted tar extraction.
Shape checks run on the staged tree before promotion of ONLY the approved cache
root. File mtimes are preserved for Cargo reuse, but arbitrary archive mode
metadata is not applied. No cache member may overwrite source/control/config
files or escape its approved root.
Raw header checks require valid framing and zero-only trailing padding before
tarfile parsing. Global PAX headers are unsupported and rejected before their
payloads are read: tarfile otherwise copies their fields into every member,
amplifying memory use. The pinned save action's GNU tar --posix uses local PAX
entries. Supported extensions are limited to 1 MiB each, 64 MiB total and 16
consecutive headers; PAX size overrides/sparse data are unsupported. Path length
is limited to 32,767 characters and depth to 128 components. Scratch archives
and private staging trees are removed on both success and ordinary failures.

The service can return a prefix match even for a primary-key lookup. Every
returned key must match the prepared exact key or its intended registry/target
fallback scope; Nextest requires exact equality only. Only a genuine absent
entry is a cold-build miss. Authentication, transport, timeout, decompression,
archive, key or shape failures fail restore and the job, never turn into misses.

No whole Cargo home, registry index/extracted sources, .cargo/git db/checkouts,
Git/Cargo configs/credentials, vendor/source trees, rustup, trusted control
checkout, or Cargo install receipts are cached. Cargo home is isolated per run.
Registry downloads are consumed through Cargo's locked checksum verification
and fresh unpacking/vendoring; never restore an extracted Cargo source/config.
Restored roots, ancestors and entries are checked for links/junctions/reparse
points and special files before cached data is used, and again before saving.
Unexpected registry/tool entries fail closed. Archive/path gates constrain
materialization, not executable behavior; these checks are not a sandbox.

On a Nextest miss, cargo install uses --locked --version =0.9.114 and an explicit
fresh .nextest-install root/target outside candidate, then copies only the EXE
and removes install state. A hit is not accepted on presence alone: its expected
tool/version is checked by execution ONLY inside the token-free compile phase.
Wrong version, empty/absent executable on a hit, invalid shape, or nonzero native
exit fails the build; no reinstall-on-corruption or success-shaped fallback.

Compiled target artifacts and Nextest are UNTRUSTED EXECUTABLE INPUTS, not
integrity-verified outputs. A malicious cache can run build scripts/test/tool
code and can affect binaries; version checks do not authenticate executable
contents. Anyone able to publish malicious cache data inside an accepted scope
can compromise this disposable build job, just like malicious upstream code.
Cache keys/fresh workspace cleaning prevent accidental stale reuse, NOT that
attack. Malicious upstream code can poison executable caches despite all gates.
The job has no injected repository API token, write token or secrets; runtime
cache authentication belongs to job infrastructure, not a repository write
token. Compile strips cache/artifact API variables from its environment before
executing candidate code; this does not make the disposable job a credential
sandbox or remove its inherent runner service access. The publisher
never restores any caches, executes cached inputs, or trusts a cache as proof.
Provenance still identifies exact source/workflow/run, not a cache-free rebuild.

Before release compilation and tests, cargo metadata --locked
identifies ALL local/path packages (including version and submodule crates);
cargo clean --package clears their artifacts/fingerprints in BOTH profiles.
Any remaining final package EXE is an error before cargo build. Thus a target
hit cannot skip local source/.tag recompilation just because restored timestamps
look fresh. Third-party dependencies remain eligible for Cargo's reuse checks.
Locked vendoring and four release binaries are mandatory on every run. x64
retains native --locked --all --no-fail-fast Nextest and upstream deploy.sh
packaging unchanged on windows-2025. ARM64 uses the
aarch64-pc-windows-msvc target, VS x64-host/arm64-target tools and
-Ctarget-feature=+crt-static, and compiles all tests with cargo test --no-run on
the x64 windows-2025 runner. It never runs upstream deploy.sh.

ARM64 packaging is a control-plane allowlist built directly from
target/aarch64-pc-windows-msvc/release: wezterm.exe, wezterm-gui.exe,
wezterm-mux-server.exe, strip-ansi-escapes.exe, plus only their same-basename
PDBs when generated. Every executable is parsed as PE/COFF and must have machine
0xAA64. The archive cannot contain conpty.dll, OpenConsole.exe, ANGLE, Mesa or
any other DLL/file. The publisher independently repeats these checks.
There is no sccache/setup action: target reuse needs no additional compiler
wrapper/download, and also covers MSVC outputs and debug test dependencies.
Genuine cache misses trigger a cold build, not build success. Pinned save's
network failures are nonfatal warnings; restore failures are fatal. Neither
behavior suppresses compile/test/package native command failures. Save runs
only after the ENTIRE compile/test/package step
succeeds and revalidates the cache paths. Exact hits are not re-saved. GitHub cache
eviction/quota or hosted-image/toolchain changes can force a full rebuild.

Request contract / coordinator handoff
--------------------------------------
Exactly eight keys are accepted (no other fields, duplicate keys or coercions):
    schema             integer 1 (not bool)
    repository         "dc0d32/nixos"
    branch             "automation/update-flake-lock"
    source_repository  "wezterm/wezterm"
    source_sha         40 lowercase hexadecimal characters
    request_id         64 lowercase hexadecimal characters
    requested_at       ISO UTC YYYY-MM-DDTHH:MM:SS[.ffffff]Z
    nonce              positive numeric STRING containing coordinator github.run_id

The nonce is the explicitly requested ADDITION to the coordinator schema:
    material = "dc0d32/nixos\nautomation/update-flake-lock\n" +
               source_sha + "\n" + nonce
    request_id = SHA256(material encoded as UTF-8).hexdigest()
There is NO trailing newline after nonce. This hash binds request identity,
not cryptographic authentication; admission comes from the fixed repository,
branch, PR and default-branch checks. A branch update of any kind supersedes
the captured request, even if it retains the same request_id. Forks, merged
or closed PRs, changed default base, ambiguous PRs and branch-ref/PR-head
disagreement are rejected. We fetch the file at the PR's immutable head SHA
and confirm wezterm/wezterm's anonymous exact-commit API returns source_sha.
An invalid/missing request fails closed; no eligible PR is a successful no-op.

Public release contract
------------------------
    build_id = source_sha + "-" + run_id + "-" + run_attempt
    tag      = "wezterm-" + build_id
    x64 archive = "WezTerm-windows-x86_64-" + build_id + ".zip"
    ARM archive = "WezTerm-windows-aarch64-" + build_id + ".zip"
There are exactly four release assets: both archives, provenance.json and
SHA256SUMS. SHA256SUMS has one "<sha256>  <name>\n" line per archive, sorted by
architecture key (aarch64 then x86_64).

provenance.json contains:
    schema=2, source_repository="wezterm/wezterm", source_sha,
    build_repository="dc0d32/wezterm-builds", run_id (positive integer),
    run_attempt (positive integer), build_id, version, success=true,
    request_id, requested_at and nonce (the accepted request values), and:
    assets.windows.x86_64
    assets.windows.aarch64
Each architecture object has exactly name, architecture, archive_root, sha256
(lowercase hex), and size (positive integer). The x86_64 root remains
"WezTerm-windows-" + version; the aarch64 root is
"WezTerm-windows-aarch64-" + version.

version is the upstream timestamp tag format YYYYMMDD-HHMMSS-<short-sha8>,
derived from the exact upstream committer date, explicitly normalized to UTC.
It is written to upstream's .tag before compilation. The x64 outer asset is renamed without rewriting upstream's ZIP. ARM64 is
independently assembled from the target-specific release directory.

The coordinator must accept an existing successful release for the SAME
source_sha even when its request_id differs. It should check manifest,
release assets/digest and workflow run provenance rather than demand that
the current request created a fresh duplicate release.

Run provenance expected by coordinator:
    workflow filename: windows-build.yml
    API run path: ".github/workflows/windows-build.yml"
    event: schedule or workflow_dispatch
    head_repository.full_name: "dc0d32/wezterm-builds"
    head_branch: repository's default branch
    run_id/run_attempt: manifest's exact numeric values
    jobs "build-x64", "build-arm64" and "validate-arm64": each completed,
    conclusion success, same run_attempt
    job "publish": publisher (never upstream code)
The publisher checks this proof before publication. The release can become
visible while publish is running. The coordinator MUST wait for that run
attempt to complete successfully before adopting the pin.

Durability, retries and retention
---------------------------------
Each poll and publisher paginates all releases and finds any normal immutable
successful release for source_sha, independently of request identity. It
checks manifest schema, naming, source version, asset digest/size/checksum,
the exact workflow and same-attempt successful build, the release tag's
commit matching the proven workflow head, and overall completed successful
run. Public asset reads have bounded 1/2/4/8/16-second backoff for
transient CDN visibility/network failures; integrity errors never retry.
There is no expiring dedup artifact or mutable "latest" tag.
Retain successful releases AND their workflow-run records permanently: the
records are part of the coordinator's proof. Artifact retention is only seven
days and has no bearing on already published releases.

No --clobber, overwrite, deletion, force-tagging, latest/nightly mutation or
tag reuse exists. A new lightweight tag is reserved with atomic POST git/refs
(never PATCH) before drafting; a tag created by another writer between the
GET and POST is rejected, not adopted. Existing identical successful releases are a read-only
no-op. Any conflicting existing tag/draft fails, not resumes or overwrites.
Failure before visibility can leave a draft: do not reuse its tag. Rerun ALL
jobs, which increments run_attempt and yields a new permanent identity.
Rerunning only publish cannot reuse an earlier attempt's build proof/artifact;
it is deliberately rejected. Rerunning a failed build derives upload naming
from the new current attempt even when the previous poll output is retained.
If publication succeeded but the run later failed, it is not dedup/adoptable;
rerun all jobs for a new attempt. Never delete a successful release to retry.

Security boundaries and unavoidable limits
-------------------------------------------
poll: anonymous public HTTP reads only, read-only default-branch checkout.
build-x64/build-arm64: separate fresh windows-2025 VMs, contents: read,
persist-credentials: false; exact
upstream clone plus recursive submodules, no GITHUB_TOKEN/secret in the build
environment; no credential persistence or write token. Only the narrowly scoped
untrusted caches described above are restored/saved in this job.
Runtime cache authentication is job infrastructure, not repository write access:
the local restore action passes it only to its Python child, never outputs or
GITHUB_ENV, and compile strips API variables before running candidate code.
Upstream Cargo build scripts execute only here; native tests and deploy.sh run
only in build-x64.
validate-arm64: fresh native windows-11-arm VM, contents/actions read only and
no secrets/write token. It revalidates the artifact and PE machines, then runs
all four executables' version/help surfaces, strip filtering, a real console
child through WezTerm's ConPTY path, and a WebGpu GUI startup/renderer smoke.
Publication requires this job's success.
publish: separate Ubuntu VM; fresh trusted build-repo checkout at workflow
head SHA; never checks out nixos PR or upstream, and never executes ZIP data.
Its own GITHUB_TOKEN addresses only allowlisted dc0d32/wezterm-builds API
routes; external nixos/wezterm/release reads are anonymous, and redirects
strip Authorization. Own artifact downloads use actions: read.

The publisher checks the artifact ID/name/run/head SHA, safely unpacks only
the two allowed files from each build artifact, validates JSON
keys/types/identity, archive
SHA256/size and SHA256SUMS, and scans every ZIP entry and CRC without extraction.
It rejects traversal/absolute paths/backslashes/ADS/Windows device names,
duplicate or case-colliding entries, symlinks/special entries, encrypted or
unsupported compression, unexpected roots/missing runtime files, ARM64
allowlists/machine types and size bombs. It creates the combined schema-2
manifest and checksums itself. It rechecks the PR/request before download,
before drafting and
immediately before the draft-to-public transition. A superseded draft stays
unpublished. GitHub APIs offer no atomic cross-repository "publish only if PR
still open" transaction: there is an irreducible interval after the final
read. The coordinator must recheck its own request before adopting any pin.

All workflow runs share a non-cancelling concurrency group to avoid two
publishers racing. GitHub may coalesce pending runs; later hourly polling is
the retry mechanism. Anonymous API rate limits can delay work.
Rust stable, Windows runner tools and Cargo dependencies are not vendored
into this service: this is provenance-addressed, not a bit-reproducible build.
No claim of Windows code signing or upstream tests' malicious-code safety.
Do not add a write token, cache access, external secrets, PR trigger,
repository_dispatch trigger or upstream checkout to publish.
